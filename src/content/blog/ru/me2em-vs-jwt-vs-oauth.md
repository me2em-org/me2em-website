JWT, OAuth 2.0 и Me2em решают одну задачу: доказать серверу, что клиент имеет право на действие. Все три выдают токен, все три проверяют его на каждом запросе, все три promise'ат безопасность.

Но за поверхностным сходством — три фундаментально разные модели доверия. И выбор между ними — не выбор технологии, а выбор **кто владеет ключом** и **кто может ошибиться безвозвратно**.

## Три модели в одном предложении каждая

**JWT** — сервер подписывает токен своим секретом или ключом. Сервер всемогущ: выдаёт, отзывает, интерпретирует. Клиент получает готовое свидетельство.

**OAuth 2.0** — клиент делегирует доступ к чужим ресурсам через авторизационный сервер. Сервер-владелец ресурса решает, что разрешить. Клиент действует в рамках делегированного.

**Me2em** — пользователь владеет seed'ом, из которого детерминированно выводятся все ключи. Клиент **сам подписывает** свои токены, а сервер только **верифицирует** их против аттестационной цепочки. Никто не владеет правом создавать чужие токены.

Разница не косметическая. Это три разных ответа на один вопрос:

> **Кому вы доверяете право создать токен с полномочиями?**

## Анатомия: что внутри токена

Начнём с структуры — она уже показывает философию.

### JWT (JSON Web Token)

```typescript
// Стандартная структура JWT:
// header.payload.signature (все три — base64url)

// Header:
{ "alg": "HS256", "typ": "JWT" }

// Payload:
{
  "sub": "user-12345",           // subject — ID из БД
  "name": "Alice",
  "role": "admin",               // права — вписаны сервером
  "iat": 1716912000,
  "exp": 1716915600
}

// Signature: HMAC-SHA256(header, payload, serverSecret)
// Или RSA/ECDSA — подпись серверным приватным ключом
```

### OAuth 2.0 Access Token

```typescript
// OAuth-токен — обычно opaque (непрозрачный):
// сервер выдаёт случайную строку и хранит её значение в БД
{
  "access_token": "eyJhbGciOi..." // случайная строка
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "def50200..."
}

// Если JWT-подобный (JWT-as-access-token):
// структура та же, что выше — но выдан через OAuth flow
```

### Me2em Session

```typescript
// Me2em session payload:
{
  "hId": "base64url-публичный-ключ-хэндла",
  "hNm": "work",
  "hPath": ["work"],              // путь в дереве деривации
  "aud": "app.example.com",       // для кого
  "scp": ["read", "write"],       // права — заявлены клиентом,
                                  // проверены сервером
  "exp": 1716915600,
  "iat": 1716912000,
  "jti": "уникальный-ID"
}

// Signature: Ed25519(handle.privateKey, payload)
// Подпись — ключом ХЭНДЛА, не серверным секретом
```

**Ключевое различие на уровне структуры:** в JWT `sub` — ссылка на БД (нужен lookup чтобы понять кто это). В OAuth `access_token` — обычно opaque (нужен introspection endpoint). В Me2em `hId` — **сам публичный ключ**, верифицируемый криптографически без lookup'а.

## Кто подписывает: сервер vs клиент

Это — главная развилка.

### JWT: сервер подписывает

```text
1. Пользователь логинится (пароль, OAuth-провайдер, ...)
2. Сервер создаёт payload { sub, role, exp, ... }
3. Сервер подписывает payload СВОИМ секретом
4. Клиент получает JWT и передаёт его при каждом запросе
5. Сервер проверяет подпись СВОИМ секретом
```

Сервер — единственный источник токенов. Он может создать токен для любого пользователя с любыми правами. Пользователь **не может** создать токен сам — и в этом сила модели (сервер контролирует выдачу), и её ограничение (сервер нужен онлайн, сервер — единственная точка компрометации).

### Me2em: клиент подписывает

```text
1. Пользователь вводит seed-фразу (один раз за сессию)
2. Детерминированно вычисляется Handle: приватный ключ
3. Клиент создаёт payload { hId, aud, scp, exp, ... }
4. Клиент ПОДПИСЫВАЕТ payload ключом ХЭНДЛА
5. Сервер проверяет подпись против публичного ключа ХЭНДЛА
   (пересчитанного из имени в токене)
```

Сервер **не может** создать токен для пользователя — у него нет его приватного ключа. Пользователь не может создать токен с расширенными правами — payload подписан, изменить поля без инвалидации подписи невозможно. Права фиксируются **при создании**, а не пересматриваются на каждом запросе.

### OAuth: промежуточный вариант

OAuth 2.0 не подписывает сам — он делегирует. Клиент получает токен от авторизационного сервера (authorization code flow, client credentials и т.д.) и предъявляет его ресурсному серверу. Токен может быть opaque (introspection) или JWT (self-contained).

Сложность OAuth — в количестве сущностей: авторизационный сервер, ресурсный сервер, клиент, владелец ресурсов, scope'ы, redirect URI'ы, refresh-токены. Это цена гибкости для сценариев "приложение A хочет доступ к данным пользователя на сервисе B".

## Сравнительная таблица

| Аспект | JWT | OAuth 2.0 | Me2em Session |
|--------|-----|-----------|---------------|
| **Кто подписывает** | Сервер | Авторизационный сервер | **Клиент (хэндл)** |
| **Основа подписи** | Серверный секрет / ключ | N/A (opaque) или серверный ключ | Детерминированный ключ хэндла |
| **Хранение сессий на сервере** | Нет (self-contained) | Да (introspection / reference token) | Нет (stateless) |
| **Отзыв** | Нет встроенного (нужен БД-черный список) | Да (refresh flow, introspection) | Да (jti + RevocationChecker) |
| **Идентичность** | Строка sub из БД | Строка из auth-сервера | **Публичный ключ** — верифицируемый |
| **Иерархия** | Нет | Нет | Да (hPath: Handle → SubHandle) |
| **Кто может подделать** | Тот, кто знает серверный секрет | Тот, кто украл токен (до expiry) | Тот, кто знает приватный ключ хэндла |
| **Пересчёт pubkey** | Не нужен | Не нужен | Да — по имени из токена |
| **Анонимность** | Низкая (sub — идентификатор в БД) | Низкая (клиент идентифицируем) | Высокая (нет связи с email/телефоном) |

## Модель доверия: кто кому верит

### JWT — доверие серверу целиком

```text
Пользователь → доверяет → Сервер → подписывает → Токен
                                    ↓
                              Сервер может:
                              - выдать любые права
                              - отозвать любую сессию
                              - расшифровать payload
                              - утратить секрет → все токены скомпрометированы
```

### OAuth — доверие трём сторонам

```text
Пользователь → доверяет → Auth-серверу → выдаёт токен
             → доверяет → Ресурс-серверу → проверяет токен
             → доверяет → Клиенту → не превысит scope
```

### Me2em — доверие криптографии

```text
Пользователь → владеет → Seed'ом → детерминирует → все ключи
Клиент → подписывает → токен → предъявляет
Сервер → верифицирует → подпись + аттестации → публичным корнем
        ← сервер НЕ может создать чужой токен
        ← сервер НЕ видит содержимое (только подпись + метаданные)
```

## Утечка: что происходит

Ключевой вопрос при выборе модели: что происходит при компрометации.

### JWT — утечка серверного секрета

```text
Секрет утёк → атакующий может выдать ТОКЕН ДЛЯ ЛЮБОГО ПОЛЬЗОВАТЕЛЯ
            → с любыми правами, любым exp, любым sub
            → до истечения текущих токенов
            → без следа (нет логов создания)
Mitigation: ротация секрета → все JWT становятся невалидными → все
            пользователи разлогинены
```

### Me2em — утечка хэндла

```text
Приватный ключ хэндла утёк → атакующий может подписать сессии ЭТОГО
                             хэндла (в рамках его прав)
Mitigation 1: revocation через attestation jti — мгновенно, все сервисы
Mitigation 2: short TTL — атака ограничена 1 часом
Mitigation 3: attestation revocation — блокирует и будущие сессии
Риск ограничен ХЭНДЛОМ — другие хэндлы того же пользователя не затронуты
```

### Me2em — утечка seed

```text
Seed утёк → атакующий может пересчитать ВСЁ ДЕРЕВО → все хэндлы
           → это полный компрометация → средства (если крипто) утеряны
           → НЕ Mitigation (детерминизм = нет ротации)
Mitigation: seed в бумаге, никогда не в устройстве, никогда в облаке
```

## Код: один сценарий, три реализации

Сценарий: пользователь хочет получить доступ к API. Смотрим, как выглядит каждый подход.

### JWT

```typescript
// Сервер:
app.post('/login', async (req, res) => {
  const user = await verifyPassword(req.body.email, req.body.password);
  if (!user) return res.status(401).send('Invalid credentials');
  
  const token = jwt.sign(
    { sub: user.id, role: user.role },
    SERVER_SECRET,
    { expiresIn: '1h' }
  );
  res.json({ token });
});

// Проверка на каждом запросе:
function authenticate(req) {
  const payload = jwt.verify(req.headers.authorization, SERVER_SECRET);
  // Look up user in DB to confirm role still valid
  const user = await db.users.findById(payload.sub);
  return user;
}
```

### OAuth 2.0

```typescript
// Шаг 1: redirect на auth-сервер
res.redirect(`https://auth.example.com/authorize?` +
  `response_type=code&client_id=${CLIENT_ID}&redirect_uri=${REDIRECT_URI}&scope=read`);

// Шаг 2: обмен code на token
const token = await fetch('https://auth.example.com/token', {
  method: 'POST',
  body: `grant_type=authorization_code&code=${code}&client_id=${CLIENT_ID}`
});

// Шаг 3: каждый запрос — introspection или local JWT verify
const introspect = await fetch('https://auth.example.com/introspect', {
  method: 'POST',
  body: `token=${token}`,
  headers: { 'Authorization': `Basic ${CLIENT_CREDENTIALS}` }
});
const { active, scope, sub } = await introspect.json();
```

### Me2em

```typescript
// Регистрация (один раз — seed на бумаге):
const identity = await Identity.fromSeed(seed);
// Все Handle уже существуют — они детерминированы

// Создание сессии (на клиенте, без сервера):
const session = await Session.create(handle, {
  audience: 'app.example.com',
  scopes: ['read', 'write'],
  ttl: 3600,
});

// Верификация (на сервере, без БД):
const verified = await Session.verifyStateless(
  session.token,
  serverIdentity,       // Identity — пересчитывает pubkey хэндла
  'app.example.com',
  revocationChecker?,   // опционально
);
// verified.scopes — права из токена
// verified.handleName — кто именно
```

## Сводная таблица

| Критерий | JWT | OAuth 2.0 | Me2em Session |
|----------|-----|-----------|---------------|
| **Кто создаёт токен** | Сервер | Auth-сервер | Клиент (хэндл) |
| **Серверный секрет** | Нужен | Нужен | **Не нужен** |
| **Stateless** | Да (self-contained JWT) | Обычно нет (introspection) | Да |
| **Отзыв** | Нет встроенного | Да (introspection) | Да (jti + RevocationChecker) |
| **Иерархия прав** | Нет | Да (scope nesting) | Да (attestation chains) |
| **Идентичность** | Строка sub из БД | Строка sub | **Публичный ключ** |
| **Анонимность** | Низкая | Низкая | Высокая |
| **Утечка секрета сервера** | Критическая | Критическая | N/A (нет серверного секрета) |
| **Утечка клиентского ключа** | N/A (клиент не хранит ключ) | N/A | Ограничена (один хэндл, один TTL, revocation) |
| **Мультидевайсность** | Требует sync | Требует sync | Детерминированная (тот же seed) |
| **Регистрация** | Email/телефон | Email/телефон | **Только seed-фраза** |
| **Делегирование** | Ограничено | Основная цель | Attestation chains |

## Когда что выбирать

| Ситуация | Рекомендация |
|----------|--------------|
| Обычный web-app с БД пользователей | JWT — отработанный стандарт |
| Мульти-сервисная архитектура с делегированием | OAuth 2.0 — отработанный стандарт |
| Криптографическая идентичность без БД | Me2em Session |
| E2EE-коммуникация | Me2em + @me2em/crypto |
| IoT-устройства с офлайн-авторизацией | Me2em + attestation chains |
| AI-агенты с детерминированными ключами | Me2em + attestation chains |
| Анонимные пользователи (без email/телефона) | Me2em |
| Обычный SaaS без криптографических требований | JWT / OAuth — не переусложняйте |

Me2em не заменяет JWT или OAuth — он решает другую задачу. Если вам нужна анонимная, детерминированная, делегируемая идентичность без серверных секретов и без БД — Me2em делает это нативно. Если вам нужна обычная авторизация в web-приложении с БД пользователей — JWT или OAuth достаточно и проще.
